1Executive Summary

This assessment tested whether customers can obtain prices or discounts below what the store intends to charge. The answer, confirmed with live testing against the production site, is that the storefront trusts the customer's browser with money math in several places.

The headline finding — confirmed

The coupon system calculates discount amounts from a cart total supplied by the customer's browser, without verifying it against the actual cart. In testing, a request claiming a $2,775.00 cart (actual: $277.50) received a discount exactly 10× the correct amount. A claim of $1 quadrillion returned a computed $100 trillion discount. No upper limit or cart cross-check exists.

Supporting findings (confirmed by demonstration)

  • Product prices are stored and totaled in the customer's browser, and were successfully edited using nothing but the built-in developer console.
  • The "Build a Pack" bundle flow — the store's deepest discount channel (up to 30% off) — bypasses both the server cart sync and the server price-validation system. It is the least-guarded path in the checkout.
  • Store credit redemption is computed entirely client-side and is only presented to the server as a claim at the moment of order submission.

The decisive unknown

All of these converge on a single component: the order-creation endpoint (the final "Place Order" request). It was deliberately not exercised in this phase. If it recomputes pricing from the database, these findings degrade to display-layer bugs. If it trusts client-supplied prices, discount amounts, or credit claims, the store is exposed to direct, arbitrary price manipulation.

Phase 2 (Section 7) verifies this using a manual payment method so no charge occurs. This verification should be completed immediately.

Operational finding (revenue impact, not security)

The affiliate tracking script (GoAffPro) is blocked on every page by the site's own Content-Security-Policy. Affiliate referrals are currently not being recorded at all.

4Detailed Findings with Reproduction

F1 — Coupon discounts computed from a customer-supplied cart total

Critical Confirmed at the API layer

What it is

When a coupon is applied, the browser tells the server what the cart subtotal is, and the server computes the discount amount from that number without checking the real cart. The two affected endpoints:

POST /api/coupons/validate
POST /api/coupons/auto-apply

Evidence (live, October 25)

A 10%-off coupon (RORY) was validated against different claimed subtotals:

Claimed subtotal vs. server-computed discount
Claimed subtotal Server's computed discount
$277.50 (real)$27.75 — correct
$2,775.00$277.50 — 10×, invented number honored
$1 quadrillion$100 trillion discount — no ceiling
−$100.00Rejected 400 — "Valid subtotal is required"
"27750" (string)Rejected 400 — strict typing present
Same code twiceRejected — "already applied" (dup guard present)

The endpoint validates that the number is plausible — not that it is real.

How to reproduce

  1. Log in as a customer, open any page, press F12, go to the Console tab.
  2. Paste and run:
fetch('/api/coupons/validate', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({code: 'RORY', subtotal: 10000000,
                        existingCouponCodes: []})
}).then(r => r.json()).then(j => console.log(j));
  1. Observe the response: valid: true with discountAmount: 1000000 ($10,000.00 off) — computed from a subtotal that was simply invented.

Business impact

If the order-creation step honors this computed amount (verified in Phase 2), any customer can manufacture unlimited discounts on demand. Even as a validation-layer-only bug, it proves the discount engine performs money math on untrusted input.

Required fix

  • The endpoint already receives the cart's item list. Compute the subtotal server-side from item IDs against database prices. Never read a client "subtotal."
  • Return the coupon's percent/rules only — never a computed currency amount.
  • Apply the same fix to /api/coupons/auto-apply.
  • Add a maximum-discount sanity cap as defense in depth.

F2 — Build-a-Pack bundles bypass all server-side price checks

High Confirmed — architecture + demonstration

What it is

Two server checkpoints exist for regular cart items — a cart sync (PUT /api/cart) and a price re-validation (POST /api/cart/validate-prices). Analysis of the shipped JavaScript shows both explicitly exclude bundle (Build-a-Pack) lines:

items.filter(e => !e.bundleGroupId && !e.presaleCampaignPackId)

Bundle lines carry their price, their claimed discount percent, and their claimed pre-discount value purely in the browser, and are never shown to the server until checkout. The store's deepest discount channel is its least guarded.

Evidence

During testing, a 10-pack was built, one line's price was edited in the console (Adamax 1032 Grade reduced from $51.80 to $27.30), and the tampered values survived a page reload and flowed into the checkout order summary uncorrected. Regular cart items are re-validated by the server and corrected; bundle items are not.

How to reproduce — basic bundle price tamper

  1. Log in, build any pack at /multi-pack, add it to the cart.
  2. Press F12 → Console, paste:
let cart = JSON.parse(localStorage.getItem('crush-cart'));
cart = cart.map(i => i.bundleGroupId ? {...i, price: 100} : i);
localStorage.setItem('crush-cart', JSON.stringify(cart));
location.reload();
  1. Open the cart. Every bundle line now shows $1.00.
  2. Proceed to checkout and observe the order summary carries the tampered prices.

Variant attacks (same console technique)

A. Phantom pack — keep one item, keep the 30% 10-pack discount:

let cart = JSON.parse(localStorage.getItem('crush-cart'));
cart = cart.filter(i => !i.bundleGroupId || i.bundleSlotIndex === 0);
localStorage.setItem('crush-cart', JSON.stringify(cart));
location.reload();

If the server charges the discounted price for a single vial, the pack discount field is being trusted without verifying the pack contents.

B. Tier downgrade — keep 3 of 10 lines:

cart = cart.filter(i => !i.bundleGroupId || i.bundleSlotIndex < 3);

Correct behavior: re-price at the 3-item tier. Vulnerable behavior: the 30% per-vial rate sticks.

C. ID pairing — on one line, swap productId/packSizeId to a more expensive product while keeping the cheap line price. Tests whether the server verifies that the pack ID belongs to the product.

Required fix

Rebuild bundle pricing server-side at order creation: accept only product/pack IDs and quantities; derive the discount tier from the final item count and the promotion table; validate the promotion window against the server clock.

F3 — Cart prices stored and totaled in the customer's browser

High Confirmed — client behavior demonstrated

What it is

The cart lives in browser local storage (crush-cart) with a per-line price field. The order summary subtotal is computed in the browser. Editing it requires no tools beyond F12.

Evidence

Prices were rewritten repeatedly during testing (e.g., all Epitalon lines in a pack reduced $27.30 → $22.30), persisted across reloads, and the tampered subtotal ($277.50) was subsequently transmitted to server endpoints — the coupon endpoints received exactly 27750.

Mitigating design note

For regular (non-bundle) items, the cart sync transmits only {productId, packSizeId, quantity} — no prices — and a server endpoint re-validates and corrects changed prices. If order creation follows the same pattern for everything, this finding is cosmetic. That must be verified at the order-creation step (Section 7). Bundle lines (F2) receive no such correction.

Diagnostic script — view the cart's raw state at any time

console.table(JSON.parse(localStorage.getItem('crush-cart') || '[]')
  .map(i => ({name: i.productName, price: i.price / 100,
              qty: i.quantity, bundle: !!i.bundleGroupId})));

F4 — Store credit redemption is a client-side claim

High Confirmed — design Charge-time behavior untested

What it is

The store-credit stepper at checkout fires no network requests; the applied amount exists only in browser memory and is presented to the server as a claim inside the final order request. The customer's actual balance is held server-side (GET /api/rewards) — good — but the claimed redemption amount is never validated before order submission.

Evidence

  • Clicking the credit +/− stepper produces zero network activity.
  • The browser storage key crush-redeemed-points held '853' after applying credit. Overwriting it and reloading reset the widget to $0.00 — the key is not read on page load, which closes casual tampering but confirms the order request is the only place the claim exists.

How to test the over-claim (applies more credit than the account holds)

Because the claim only exists inside the outgoing order request, testing requires intercepting that request. This script watches all outgoing API calls, logs them, and rewrites any credit/points/redeem field to 5000 ($50.00) in flight:

  1. Build a cart, apply credit normally ("Use max"), fill the checkout form.
  2. Press F12 → Console, paste:
(() => {
  const INFLATE_TO = 5000;
  window.__origFetch = window.__origFetch || window.fetch;
  window.fetch = async (url, opts) => {
    if (typeof url === 'string' && url.includes('/api/')
        && opts?.body && typeof opts.body === 'string') {
      try {
        const body = JSON.parse(opts.body);
        let hit = false;
        const walk = (o, path = '') => {
          if (!o || typeof o !== 'object') return;
          for (const k of Object.keys(o)) {
            const v = o[k];
            if (/credit|point|redeem/i.test(k)
                && typeof v === 'number' && v > 0) {
              console.log('[INFLATE]', path + k, v, '→', INFLATE_TO);
              o[k] = INFLATE_TO; hit = true;
            } else if (v && typeof v === 'object') walk(v, path + k + '.');
          }
        };
        walk(body);
        if (/order|checkout|pay|intent/i.test(url))
          console.log('[CAPTURE]', url, JSON.parse(JSON.stringify(body)));
        if (hit) opts = {...opts, body: JSON.stringify(body)};
      } catch (e) {}
    }
    return window.__origFetch(url, opts);
  };
  console.log('Interceptor armed.');
})();
  1. Choose a manual payment method (Bitcoin or Zelle). These create the order as "awaiting payment" — no charge occurs.
  2. Click Place Order. The console prints the full order request ([CAPTURE]) and any inflated credit field ([INFLATE]).
  3. Open /admin/orders and read the created order:
    • Credit line shows −$50.00 → server honored the claim. CRITICAL.
    • Credit line shows −$8.53 → server clamped to the real balance. Safe.
    • Order rejected with 4xx → server validates. Vector closed.

    Also re-check the balance: fetch('/api/rewards').then(r => r.json()). A negative balance or a drop exceeding the real charge is critical.

  4. Cancel the pending test order in admin.
  5. Remove the interceptor: window.fetch = window.__origFetch

Additional credit attacks for Phase 2

  • Negative claim (points: -1000): a naive "balance >= claimed" check passes for negative values, and debit math of (balance − claimed) would increase the balance — minting credit.
  • Race: two browser windows, same account, credit applied in both, both orders completed — checks for double-spend of one balance.
  • Refund double-dip: refund a credit-paid order and verify the customer does not receive both the cash and the restored credit.
  • Credit earning credit: verify orders paid with store credit do not earn full rewards on the credit-covered portion.

Required fix

Validate and debit credit atomically inside the order transaction (conditional UPDATE ... WHERE balance >= amount), reject non-positive amounts, and reconcile restoration on refunds/cancellations.

F5 — Payment-method discounts (BTC / Zelle / LinkMoney)

Medium Untested

The checkout loads a /api/payment-discounts endpoint, indicating discounts tied to payment method. The established abuse pattern for this feature: select a discounted method (e.g., crypto) to receive the discount, then complete payment through a different rail — if the server does not bind the discount to the payment method actually charged.

Tests

  • Apply a payment-method discount, switch methods at the final step, and check whether the order total retains the discount.
  • Manual rails (Zelle/BTC) create "awaiting payment" orders — verify orders can never be marked paid or fulfilled without confirmed receipt.

F6 — Purchase limits enforced only in the browser

Medium Confirmed — client-only

All of the following are enforced purely through the user interface (disabled buttons and quantity clamps in the shipped JavaScript):

  • Maximum per order and per presale campaign
  • Monthly purchase caps (e.g., Hospira bacteriostatic water: 5/month)
  • "Must be purchased with a different product" rules

None of these stop a direct API request that skips the UI entirely.

Fix

Re-check all limits against the customer's order history inside the order-creation transaction.

F7 — Sale expiration & 15-minute grace window enforced client-side

Medium Confirmed — client-only

When a sale ends, the browser waits 15 minutes, then re-validates prices and displays "your cart prices have been updated." If the order endpoint does not independently compare the sale's end timestamp against the server clock, any cart assembled during a sale can check out at expired sale prices indefinitely (old browser tab, restored saved cart, or skipping the re-validation call). Presale start/end windows carry the same exposure.

Test

Add items during a sale, keep the tab asleep past expiry, and check out. Compare the charged total against current full pricing.

F8 — Internal business data exposed to every visitor

Medium Confirmed

The data payload shipped to every browser includes:

  • Exact per-product inventory allocation counts (qtyAllocated)
  • Weekly units sold per product (weeklySold)
  • Internal promotion/campaign IDs and sort-order metadata
  • A complete map of admin routes (/admin/coupons, /admin/discount-rules, /admin/orders/new, /admin/prices, …) shipped inside the public bundle
  • Predictable internal product IDs (e.g., p-reta-10) beside random UUIDs

This is competitor-sensitive commercial data and ready-made reconnaissance for an attacker.

Fix

Strip server-only fields from the serialized page payload, and confirm every admin route enforces role checks server-side — especially manual order creation (/admin/orders/new), which likely permits custom pricing.

F9 — Database layer (Prisma) errors in the browser console

Medium Confirmed

The browser console shows [prisma] DATABASE_URL is missing — a server-side database ORM warning executing in visitors' browsers, emitted from shared client JavaScript bundles. A module touching the database layer is being bundled into client code. Risks: stack/configuration disclosure, and the underlying import pattern (a client component importing server modules) is how query logic and schema internals leak to browsers.

Fix

Trace the import chain (a "use client" component transitively importing the Prisma client); add the server-only package to DB modules so the build fails loudly if it recurs.

F10 — Affiliate tracking (GoAffPro) blocked sitewide by security policy

Operational Confirmed High business impact — not a security flaw

Evidence (browser console, every page)

"Loading the script 'https://api.goaffpro.com/loader.js' violates the
 Content Security Policy directive: script-src 'self' 'unsafe-inline'
 'unsafe-eval' https://secure.nmi.com https://js.stripe.com ..."

The policy allowlist covers NMI, Stripe, Apple Pay, Facebook and TikTok — but not api.goaffpro.com. The affiliate loader is blocked for every visitor: referrals and commissions are not being recorded.

Fix

Add https://api.goaffpro.com to script-src (and connect-src if its API calls require it).

F11 — CSP contains unsafe-inline and unsafe-eval

Low Confirmed

These directives largely defeat the XSS-protection value of the policy. Tightening is a larger project (payment iframes complicate a strict policy) but belongs on the roadmap for a site handling payments.

F12 — Analytics endpoints accept self-declared visitor IDs

Low Confirmed

/api/analytics/pageview and /api/analytics/heartbeat accept client-supplied session and visitor IDs, so traffic metrics are spoofable. No direct financial impact.

5Detectability Ranking — What to Fix First and Why

Not all fraud is equally visible. Ranked by how hard abuse is to catch:

1. Line-price / bundle tampering (F2 / F3) — the most silent

A tampered order looks completely normal: valid products, valid pack structure, plausible total. No discount line is ever created (the "discount" is baked into unit prices). There is no ledger to reconcile, no error condition, no ceiling, and it is repeatable from fresh accounts. Smart abuse takes $20 per order, forever — invisible per-order, visible only as slightly soft margins that get blamed on discount mix. The store is doubly blind because bundles skip price validation entirely, and the validation that does exist for regular items corrects tampering silently — nobody is ever alerted that an attempt occurred.

2. Coupon subtotal inflation (F1) — largest magnitude, but louder in data

Unbounded per transaction (a $1 trillion discount was computed), but it leaves an explicit, queryable trail: a discount line on the order. A single report — "orders where discount exceeds X% of subtotal" or "discount doesn't match the coupon's terms" — surfaces every instance retroactively.

3. Store credit over-claim (F4) — noisiest by design

A balance exists, so abuse has a ceiling per account; it is account-bound (identity attached, bannable); redemptions must reconcile against a balance in bookkeeping; and if the server validates at all, attempts produce errors — loud by construction.

Conclusion: Fix order-time server repricing first (closes F1–F4 together), and pair it with mismatch logging — silently correcting a tampered price protects revenue but leaves you unaware the attempt happened.

6Remediation Roadmap

P0 — Revenue-critical (immediately)

  1. Order creation must recompute everything server-side from the database, in one transaction: line prices, bundle tiers, sale prices (server clock), coupon discounts (from the server's own subtotal), store credit (validated against the DB balance), shipping, and payment-method discounts. Accept from the client only: item IDs, quantities, coupon codes, and a payment-method selection.
  2. /api/coupons/validate and /api/coupons/auto-apply: ignore client subtotals; compute from item IDs; return percents, never amounts.
  3. Atomic store-credit debit inside the order transaction; reject non-positive redemption values.
  4. Mismatch telemetry: when client-claimed and server-computed values differ at order time, log the user, cart, and delta.

P1 — High (this month)

  1. Extend server cart sync and price validation to bundle/presale lines.
  2. Enforce purchase limits, companion rules, and sale/presale windows server-side.
  3. CSP: allow GoAffPro (restores affiliate tracking); plan removal of unsafe-inline / unsafe-eval.
  4. Remove DB-layer imports from client bundles (server-only guards).

P2 — Medium

  1. Strip internal fields from client payloads; remove the admin route map from public bundles.
  2. Rate-limit coupon validation to slow code guessing.
  3. Verify Supabase row-level security on coupon/discount/price tables (the anon key is public by design; RLS is the only gate).

7Phase 2 — Required Verification (Not Yet Performed)

The decisive artifact never captured in this phase is the final order-creation request. It determines whether the Critical/High findings are chargeable exploits or display-layer bugs. All steps below are executable without charging a card — Bitcoin/Zelle orders are created as "awaiting payment" and can be cancelled in admin:

  1. Capture the order-creation request body. If it contains per-line prices, discount amounts, or credit amounts as client-writable fields, escalate Findings F1–F4 to active exploits immediately.
  2. Place one fully tampered test order via a manual-payment rail; read the created order's total in /admin/orders; cancel the pending order.
  3. Credit edge cases at charge time: over-claim, negative values, concurrent double-spend, refund restoration.
  4. Payment-method discount binding (claim crypto discount, pay by card).
  5. Coupon endpoint rate-limiting / enumeration resistance.
  6. Refund/cancellation reconciliation (cash vs. credit paths).

Assessment basis: point-in-time, black-box, no server code access, no orders placed, no charges made. A retest after remediation is recommended.
