The one principle behind every fix in this document: the client is an untrusted witness. 2Executive Summary

Headline — confirmed live

The coupon engine computes discounts from a cart total supplied by the customer's browser. Claimed $2,775 (real: $277.50) → 10× discount honored. Claimed $1 quadrillion → $100 trillion discount computed. No ceiling, no cart cross-check.

  • Cart prices live in the browser and were edited with only the dev console; tampered prices survived reload and flowed into the checkout summary.
  • Build-a-Pack bundles — the deepest discount channel (up to 30%) — bypass both server cart sync and server price validation.
  • Store credit redemption is a client-side claim first presented inside the final order request.

Decisive unknown: the order-creation endpoint was deliberately not exercised. If it recomputes from the database, F1–F4 degrade to display bugs; if it trusts client values, they are direct price-manipulation exploits. Verification procedure is in Section 6 and is safe to run (manual payment rails create cancellable "awaiting payment" orders).

Detectability note (why fix order matters): line-price/bundle tampering is the most silent abuse (no discount line, no ledger, no error, repeatable). Coupon inflation is loudest in magnitude but leaves a queryable discount line. Credit over-claim is noisiest (balance ceiling, account-bound). Fix order-time server repricing first — it closes F1–F4 together — and pair it with mismatch logging, because today's silent price-correction means attack attempts are never even recorded.

F1 — Coupon discounts computed from a customer-supplied cart total

CriticalConfirmed at the API layerProbable files: app/api/coupons/validate/route.ts, app/api/coupons/auto-apply/route.ts PROBABLE

What happens

The client POSTs a coupon code and the subtotal. The server multiplies and returns a currency amount, never looking at the cart. Input hygiene exists (negatives and strings rejected 400, duplicate codes rejected) but the value's truthfulness is never checked, and no upper bound exists.

Fix implementation — server-side subtotal, caps, percents-only responses reference code

Change the contract: the client sends item IDs + quantities + the code. The server prices the cart (shared priceCart, see F2/F3) and computes the discount itself. A display amount may be returned, but the order endpoint must recompute it regardless.

app/api/coupons/validate/route.ts
import { NextResponse } from "next/server";
import { prisma } from "@/lib/prisma";
import { priceCart } from "@/lib/pricing";      // F2/F3 — server pricing
import { rateLimit } from "@/lib/rateLimit";    // any limiter; 10/min/IP

export async function POST(req: Request) {
  if (!rateLimit(req)) return NextResponse.json({ error: "Slow down" }, { status: 429 });

  const { code, items } = await req.json();          // NOTE: no client subtotal
  if (typeof code !== "string" || !Array.isArray(items))
    return NextResponse.json({ valid: false, reason: "bad_request" }, { status: 400 });

  const coupon = await prisma.coupon.findUnique({ where: { code: code.toUpperCase() } });
  if (!coupon || !coupon.active || (coupon.expiresAt && coupon.expiresAt < new Date()))
    return NextResponse.json({ valid: false, reason: "invalid_or_expired" });

  const priced = await priceCart(prisma, items);     // server-computed subtotal
  const discountCents = computeCouponDiscount(coupon, priced.subtotalCents);

  return NextResponse.json({ valid: true, code: coupon.code, discountCents });
}

export function computeCouponDiscount(coupon, subtotalCents) {
  const raw = coupon.percentOff
    ? Math.floor(subtotalCents * coupon.percentOff / 100)
    : Math.min(coupon.amountOffCents ?? 0, subtotalCents);
  // Defense in depth: per-coupon cap and absolute cap, never more than the subtotal
  const cap = Math.min(coupon.maxDiscountCents ?? 100_000, 100_000); // $1,000 absolute
  return Math.max(0, Math.min(raw, cap, subtotalCents));
}

Apply the identical change to /api/coupons/auto-apply. Any client code that previously sent subtotal must be updated to send items (it already has them).

F2 — Build-a-Pack bundles bypass all server-side price checks

HighConfirmed — architecture + demonstrationProbable files: cart store chunk, app/api/cart/route.ts, app/api/cart/validate-prices/route.ts PROBABLE

Root cause (observed in shipped JS)

Both server checkpoints explicitly exclude bundle and presale lines:

items.filter(e => !e.bundleGroupId && !e.presaleCampaignPackId)

Bundle lines carry price, bundleDiscountPercent, and bundleOriginalPriceCents purely in the browser. A line edited from $51.80 → $27.30 survived reload and flowed into the checkout summary uncorrected.

Reproduction scripts — tamper, phantom pack, tier downgrade, ID pairing 4 variants

Phantom pack — keep 1 of 10 lines, keep the 30% claim:

localStorage.setItem('crush-cart', JSON.stringify(cart));

Tier downgrade — keep 3 of 10 lines; correct behavior is re-pricing at the 3-item tier:

Fix implementation — shared server-side pricing module (also fixes F3, F7) reference code

One module prices any cart from database truth: base prices, sale prices (server clock — fixes F7), and bundle tiers derived from the final item count per bundle group. Client-sent prices and percents are never read.

lib/pricing.ts
import "server-only";

// items: [{ productId, packSizeId, quantity, bundleGroupId? }]
export async function priceCart(tx, items) {
  const packSizeIds = [...new Set(items.map(i => i.packSizeId))];
  const packSizes = await tx.packSize.findMany({
    where: { id: { in: packSizeIds } },
    include: { product: true, saleCampaign: true },
  });
  const byId = new Map(packSizes.map(p => [p.id, p]));
  const now = new Date();                       // server clock — F7

  // Bundle tier lookup from the FINAL count per bundleGroupId — F2
  const bundleCounts = {};
  for (const i of items)
    if (i.bundleGroupId) bundleCounts[i.bundleGroupId] =
      (bundleCounts[i.bundleGroupId] ?? 0) + i.quantity;

  const promo = await tx.bundlePromo.findFirst({
    where: { endsAt: { gt: now } }, orderBy: { endsAt: "desc" },
  });
  const tierFor = (count) => !promo ? 0 :
    (promo.tiers.filter(t => count >= t.minQty).pop()?.percentOff ?? 0);

  let subtotalCents = 0;
  const lines = items.map(i => {
    const ps = byId.get(i.packSizeId);
    if (!ps || ps.productId !== i.productId)    // ID-pairing check — F2 variant C
      throw new Error("INVALID_ITEM:" + i.packSizeId);

    let unit = ps.priceCents;
    const sc = ps.saleCampaign;
    if (ps.salePriceCents && sc && sc.startsAt <= now && now <= sc.endsAt)
      unit = ps.salePriceCents;                  // sale only if live on server clock

    if (i.bundleGroupId) {
      const pct = tierFor(bundleCounts[i.bundleGroupId]);
      unit = Math.floor(unit * (100 - pct) / 100);
    }
    const lineCents = unit * i.quantity;
    subtotalCents += lineCents;
    return { ...i, unitCents: unit, lineCents };
  });

  return { lines, subtotalCents };
}

F4 — Store credit redemption is a client-side claim

HighDesign confirmedCharge-time untested

What happens

  • The credit +/− stepper fires zero network requests; the claim exists only in browser memory until the order request.

Fix implementation — atomic, guarded debit inside the order transaction reference code
lib/credit.ts
import "server-only";

export async function debitCredit(tx, userId, cents) {
  if (!Number.isInteger(cents) || cents <= 0)
    throw new Error("BAD_CREDIT_AMOUNT");          // kills the negative-mint attack
  const updated = await tx.$executeRaw`
    UPDATE "RewardAccount"
    SET "balanceCents" = "balanceCents" - ${cents}
    WHERE "userId" = ${userId} AND "balanceCents" >= ${cents}`;
  if (updated === 0) throw new Error("INSUFFICIENT_CREDIT");  // race-safe: single UPDATE
  return cents;
}

// On refund/cancel, restore inside the same transaction, and only the
// portion that was actually paid in credit:
export async function restoreCredit(tx, userId, cents) {
  if (cents > 0) await tx.$executeRaw`
    UPDATE "RewardAccount" SET "balanceCents" = "balanceCents" + ${cents}
    WHERE "userId" = ${userId}`;
}

Also verify in Phase 2: concurrent double-spend (two windows, one balance), refund double-dip (cash + restored credit), and that credit-paid portions do not earn new rewards.

F6 — Purchase limits enforced only in the browser

MediumConfirmed — client-only

Max-per-order, monthly caps (e.g., bacteriostatic water 5/month), and "must be purchased with another product" rules exist only as disabled buttons and quantity clamps. Direct API requests skip the UI entirely.

Fix implementation — server-side limit checks in the order transaction reference code 
async function enforcePurchaseLimits(tx, userId, items) {
  const monthStart = new Date(); monthStart.setDate(1); monthStart.setHours(0,0,0,0);
  for (const item of items) {
    const limit = await tx.purchaseLimit.findFirst({ where: { packSizeId: item.packSizeId } });
    if (!limit) continue;
    const prior = await tx.orderItem.aggregate({
      _sum: { quantity: true },
      where: { packSizeId: item.packSizeId,
               order: { userId, createdAt: { gte: monthStart },
                        status: { notIn: ["cancelled"] } } },
    });
    if ((prior._sum.quantity ?? 0) + item.quantity > limit.maxPerMonth)
      throw new Error("LIMIT_EXCEEDED:" + item.packSizeId);
    if (limit.requiresCompanion) {
      const hasCompanion = items.some(x => x.packSizeId !== item.packSizeId);
      if (!hasCompanion) throw new Error("COMPANION_REQUIRED:" + item.packSizeId);
    }
  }
}

F7 — Sale expiration & 15-minute grace window enforced client-side

MediumConfirmed — client-only

The browser waits 15 minutes after a sale ends, then re-validates and shows "your cart prices have been updated." A sleeping tab, restored cart, or skipped re-validation may preserve expired prices indefinitely. Test: assemble a cart during a sale, sleep past expiry, check out, compare against full price.

Fix covered by F2

Already fixed by priceCart (F2): sale prices apply only when startsAt <= now <= endsAt using the server clock at order time. The 15-minute grace window may remain as a client-side UX courtesy, but it must have no effect on the charged total. Same check covers presale start/end windows.

Order creation recomputes everything server-side, in one transaction (reference below): line prices, bundle tiers, sale prices (server clock), coupons (server subtotal), credit (atomic debit), shipping, payment-rail discount. Client sends only item IDs, quantities, coupon codes, and a payment-method choice.
  2. F1: coupon endpoints ignore client subtotals; caps added.
  3. F4: atomic credit debit; reject non-positive amounts.
  4. Mismatch telemetry: when client-claimed and server-computed values differ at order time, log user, cart, and delta.

app/api/orders/route.ts — INFERRED path; adapt to the real endpoint found in Phase 2
import { NextResponse } from "next/server";
import { prisma } from "@/lib/prisma";
import { priceCart } from "@/lib/pricing";
import { debitCredit } from "@/lib/credit";
import { computeCouponDiscount } from "@/app/api/coupons/validate/route";
import { getSessionUser } from "@/lib/auth";

export async function POST(req: Request) {
  const user = await getSessionUser(req);
  if (!user) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });

  const body = await req.json();
  // Accept ONLY these. Ignore any prices/totals/credits the client volunteers.
  const { items, couponCodes = [], creditToApplyCents = 0, paymentMethod } = body;

  try {
    const order = await prisma.$transaction(async (tx) => {
      // 1. Server pricing: base + sales (server clock) + bundle tiers   [F2,F3,F7]
      const priced = await priceCart(tx, items);

      // 2. Coupons against the SERVER subtotal                          [F1]
      let couponCents = 0;
      for (const code of couponCodes) {
        const c = await tx.coupon.findUnique({ where: { code: String(code).toUpperCase() } });
        if (c?.active && (!c.expiresAt || c.expiresAt > new Date()))
          couponCents += computeCouponDiscount(c, priced.subtotalCents);
      }

      // 3. Payment-rail discount bound to the chosen method             [F5]
      const pm = await tx.paymentDiscount.findFirst({ where: { method: paymentMethod, active: true } });
      const pmCents = pm ? Math.floor((priced.subtotalCents - couponCents) * pm.percentOff / 100) : 0;

      // 4. Purchase limits                                              [F6]
      await enforcePurchaseLimits(tx, user.id, items);

      // 5. Credit: atomic, guarded debit                                [F4]
      const creditCents = creditToApplyCents > 0
        ? await debitCredit(tx, user.id, Math.min(creditToApplyCents,
            priced.subtotalCents - couponCents - pmCents))
        : 0;

      // 6. Shipping from the POST-discount total
      const preShip = priced.subtotalCents - couponCents - pmCents - creditCents;
      const shippingCents = preShip >= 20000 ? 0 : await getShippingCents(body.address);

      // 7. Mismatch telemetry — see attempts even when we correct them
      if (body.claimedSubtotalCents && body.claimedSubtotalCents !== priced.subtotalCents)
        await tx.securityEvent.create({ data: { userId: user.id, kind: "PRICE_MISMATCH",
          payload: { claimed: body.claimedSubtotalCents, actual: priced.subtotalCents, items } } });

      // 8. Persist with server-computed numbers only
      return tx.order.create({ data: {
        userId: user.id,
        subtotalCents: priced.subtotalCents,
        discountCents: couponCents + pmCents,
        creditAppliedCents: creditCents,
        shippingCents,
        totalCents: preShip + shippingCents,
        paymentMethod,
        status: paymentMethod === "card" ? "pending_capture" : "awaiting_payment",
        items: { create: priced.lines.map(l => ({
          packSizeId: l.packSizeId, quantity: l.quantity, unitCents: l.unitCents })) },
      }});
    });
    return NextResponse.json({ orderId: order.id });
  } catch (e) {
    const known = ["INSUFFICIENT_CREDIT","BAD_CREDIT_AMOUNT","LIMIT_EXCEEDED",
                   "COMPANION_REQUIRED","INVALID_ITEM","PAYMENT_METHOD_MISMATCH"];
    const msg = String(e?.message ?? e);
    if (known.some(k => msg.includes(k)))
      return NextResponse.json({ error: msg }, { status: 400 });
    throw e;
  }
}
